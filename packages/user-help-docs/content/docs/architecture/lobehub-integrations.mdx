# LobeHub Integrations Reference

The complete inventory of **where QwkSearch and LobeHub touch each other**. The
strategy doc is [LobeHub Packages Migration Plan](./lobe-packages-migration-plan)
(what we're building toward) and the running work list is
[LobeHub Migration To-Do](./lobehub-migration-todo). This page is the *map*:
what exists today, in which file, and what it depends on.

Scope: `packages-lobe/` — the adapted LobeHub v2.2.13 monorepo that runs as one
Cloudflare Worker. Keep it current whenever an integration is added, moved or
removed; it is the merge contract against upstream LobeHub, so every entry
should name real files.

## Direction of the integration

The dependency runs **one way**: QwkSearch code is added *into* the LobeHub tree.
No package under `packages/` or `apps/` depends on `@lobehub/*` or `@lobechat/*`
— verified by the absence of those names in every workspace `package.json`. That
matters for the license gate: the QwkSearch workspace is not a LobeHub derivative
work; `packages-lobe/` is.

The two workspaces stay separate (bun/turbo vs pnpm). The only bridges are
**published npm packages** and **shared Cloudflare bindings** — never workspace
links. See §1 of the migration plan for why merging them is not on the table.

The npm bridges in place today, all declared in `packages-lobe/package.json` and
resolved from the registry rather than `../packages/`:

| Package | Source of truth | Used by |
|---|---|---|
| `extract-webpage` | `packages/extract-webpage` | F2 — `extractContentAndCite` over rendered HTML |
| `extract-youtube` | `packages/extract-youtube` | F2 — the YouTube transcript tier |
| `extract-pdf` | `packages/extract-pdf` | F2 — the PDF/arXiv tier |

Publishing is the update path: a fix in `packages/extract-*` reaches the engine
through `npm publish` (the `ship` script in each package) and a version bump in
`packages-lobe/package.json`, not through a workspace link.

### F1 — Article panel contract

- Opens on any external link click inside a chat message; modifier and middle
  clicks keep the browser default.
- Programmatic open:
  `window.dispatchEvent(new CustomEvent('qwksearch:open-article', { detail: { url } }))`.
- `GET /api/doc/article?url=…` returns a cached article (hit count tracked) or
  runs F2 fresh. `POST /api/doc/article` stores a Q&A pair or updates follow-ups.
- Q&A and follow-ups run through LobeHub's `AiGenerationService`, so the signed-in
  user's own providers and key vaults apply — no separate key path.

### F2 — Extraction chain contract

The seam that makes the engine's article panel extract the way qwksearch.com does.

```
GET /api/doc/article?url=…
  → classifyUrl(url) → UrlKind
    → tiersForUrl(kind)
      ├─ youtube │ pdf  → [extractViaQwkSearch]
      └─ article        → [extractViaQwkSearch, extractViaScraper, extractViaTavily, extractViaCrawler]
                             │                    └─ rendered HTML → extractContentAndCite
                             └─ extract-webpage extractContent()
                                  ├─ YouTube  → extract-youtube (transcript)
                                  ├─ PDF      → extract-pdf
                                  ├─ DOCX / Google Docs → export URL → mammoth
                                  └─ HTML     → linkedom + readability/mercury + citation extraction
```

| Concern | Behavior |
|---|---|
| Loading | `extract-webpage` is imported through a memoised, injectable loader (`loadExtractWebpage`). A failed import returns `{ error }` like any other tier failure — it never takes the Worker down, and tests inject a fake module instead |
| Why the package root | The barrel deliberately excludes `seektopic/` and `utils/documents`, so `@huggingface/transformers` and `chat-agent-toolkit` stay out of the Worker bundle even though they are dependencies of the package |
| `linkedom` | **Not shimmed.** `vite.worker.config.ts` used to alias it to a throwing stub because LobeHub only reached it from the dev-server template rewriter. It is pure JS, runs on workerd, and `extract-webpage` parses every page with it |
| Bundle cost | 7.39 MB → 7.93 MB gzipped, against Cloudflare's 10 MB limit |
| Kind routing | `youtube` and `pdf` run tier 0 alone — the later tiers render HTML, which for those URLs is page chrome, not the transcript or the document. Serving that is worse than reporting the failure |
| Rejected up front | `invalid`, `search-engine`, and `video` (Vimeo/Dailymotion/Twitch — no transcript route) |
| Scraper tier | On a successful render, the HTML goes through `extractContentAndCite` (`articleFromRenderedHtml`) so the byline survives the bot check; falls back to LobeHub readability |
| Field mapping | `fromQwkArticle` narrows the extractor's wider types onto the D1 columns — `author_type` (number \| string → text) and `error` (number \| string → text). `content` (markdown, read by the AI Q&A path), `source`, `word_count` and `cite` are filled in only when the extractor did not resolve them |

No upstream LobeHub file is edited for this. `extract.ts` and the new
`extractQwkSearch.ts` both live under `worker/`; the only build-side change is
*removing* the `linkedom` alias.

### F2a — Extraction settings contract

The chain used to read its configuration inline: `['en']` for transcript
languages, an APA-shaped citation, `process.env.SCRAPER_URL` inside the tier
that used it. `extractSettings.ts` replaces all of it with one resolved
`ExtractionSettings`, folded out of three layers.

```
DEFAULT_EXTRACTION_SETTINGS          shipped behaviour
  ← extractionSettingsFromEnv(env)   Worker vars + secrets   (operator)
  ← UserExtractionOverrides          persisted preferences   (signed-in user)
  ← ClientExtractionOverrides        ?cite= / ?lang=         (any caller)
      ↓
  tiersForUrl(url, kind, settings) → tiers bound to it, each tagged with `tierId`
```

| Concern | Behavior |
|---|---|
| Validation | Every value is normalized on the way in — language tags matched against a BCP-47 shape and capped at 5, numbers clamped, enums matched case-insensitively. A value that fails falls back to the layer below; nothing throws, because a bad preference must not become a 500 on an article fetch |
| Layer asymmetry | `ClientExtractionOverrides` is a strict subset of `UserExtractionOverrides`, which is a strict subset of the settings. Hosts and credentials (`scraperUrl`, `scraperApiKey`, `tavilyApiKey`, `pdfProcessorUrl`, `proxy`) resolve **from the environment only** — a caller-supplied backend URL would make `/api/doc/article` an open request proxy and leak the configured bearer token to it |
| `pdfProcessor` | Withheld from the client layer as well: `docling` OCRs every page, so selecting it is compute amplification rather than a preference |
| Citation styles | `apa` (default, unchanged output), `mla`, `chicago`. The extractor emits APA only, so a non-APA style is rebuilt from `author_cite` / `title` / `source` / `date`; APA keeps the extractor's own string, which came from its 90k-name database |
| Cache interaction | `articleCache` is keyed by URL and holds one `cite`. A non-APA request re-renders the citation from the cached columns instead of fragmenting the cache per style |
| Tier selection | `settings.tiers` filters the per-kind chain and can legitimately empty it (`QWKSEARCH_EXTRACT_TIERS=scraper` + a PDF URL). The caller then gets the "no extraction tier configured" error rather than a tier the operator disabled |
| Diagnostics | `redactExtractionSettings` returns the settings with each credential replaced by a boolean, so they can be logged or surfaced in the settings pane |
| Where the user layer lives | `extractionPreferences.ts` on the D1 `extraction_settings` table — see F2b |

Env vars, all optional and all defaulted: `QWKSEARCH_CITATION_STYLE`,
`QWKSEARCH_EXTRACT_LANGUAGES`, `QWKSEARCH_EXTRACT_TIMEOUT`,
`QWKSEARCH_EXTRACT_TIERS`, `QWKSEARCH_SCRAPER_DEADLINE_MS`,
`PDF_PROCESSOR`, `PDF_PROCESSOR_URL`,
`QWKSEARCH_EXTRACT_PROXY`, `QWKSEARCH_EXTRACT_THIRD_PARTY_BACKUP`. The existing
`SCRAPER_URL`, `SCRAPER_API_KEY` and `TAVILY_API_KEY` keep their names, so no
deployment needs to change.

### F2b — Extraction preferences contract

F2a defined a user layer and gave it no storage: `UserExtractionOverrides` was a
type the resolver accepted and nothing ever produced. This is the layer's
storage and its API.

```
GET/PUT/DELETE /api/doc/extraction-settings   (worker/routes/qwksearch/extractionSettings.ts)
  → extractionPreferences.ts
    → D1 `extraction_settings` (userId PRIMARY KEY, overrides JSON, updatedAt)

GET /api/doc/article
  → userExtractionOverridesForRequest(headers)   ← the same table
    → resolveExtractionSettings(env, userOverrides, clientOverrides)
```

| Concern | Behavior |
|---|---|
| Storage | One row per LobeHub Better Auth user id on the same D1 database as favorites and documents. A JSON blob, not a column per setting — the type is the schema, so a new knob is a change to `UserExtractionOverrides` rather than a D1 migration |
| Why D1, not LobeHub's `user_settings` | Postgres `user_settings` is the plan's long-term home for settings *panes*, but reading it from a Hono Worker route would couple the extraction chain to Hyperdrive for a six-field preference blob, and adding a namespace to it means an upstream type edit plus a Postgres migration. The identity is still LobeHub's; only the blob is QwkSearch's |
| Validation | Twice — `normalizeOverrides` on write and again on read. The write pass is the gate; the read pass means a row left by an older build, a hand-edited row, or a knob since removed cannot push an unvalidated value into the chain |
| Response shape | `{ overrides, effective, options }`. `overrides` is what the user set, `effective` is what is actually in force once the environment is folded in, `options` carries the enums and the timeout bounds so the pane does not hard-code them |
| What `effective` hides | Everything the user cannot set collapses to a presence flag under `configured` (`scraperUrl`, `scraperApiKey`, `tavilyApiKey`, `pdfProcessorUrl`, `proxy`). A proxy or scraper URL can carry basic-auth credentials in its userinfo, so the pane learns *whether* one is configured, never what it is |
| Write semantics | PUT replaces rather than merges — the pane sends the whole set, and a merge would leave no way to clear a field. The response echoes what was stored, which differs from what was sent whenever a value failed validation. DELETE returns the user to the operator's configuration |
| Auth | All three verbs require a session; the anonymous equivalent is `?cite=` / `?lang=` on the article route |
| Anonymous cost | `/api/doc/article` still serves signed-out callers. A request with no `cookie` header skips the session lookup entirely, so the anonymous path pays no auth round-trip |
| Failure | Reads never throw: an unreadable row, unparseable JSON or a D1 outage resolves to `{}` and the article is extracted on the operator's configuration |

Precedence, lowest to highest: shipped default → Worker env → the user's saved
overrides → `?cite=` / `?lang=` on the request.

No upstream LobeHub file is edited for this. The route, the preferences module
and the table are new; `worker/app.ts` gains one mount line and the article
route one `await`.

### F2c — Extraction settings pane

The client of F2b, and the first QwkSearch surface inside LobeHub's own settings
shell rather than beside it. `/settings/extraction`.

```
src/features/Settings/extraction/
  index.tsx           SettingHeader + the form
  api.ts              GET/PUT/DELETE /api/doc/extraction-settings
  formState.ts        form values ⇄ UserExtractionOverrides (pure)
  features/ExtractionForm.tsx
```

| Concern | Behavior |
|---|---|
| Route | None added. `desktopRouter.shared.tsx` already routes `/settings/:tab` to the tab page, so registration is the `SettingsTabs.Extraction` enum member plus the two `componentMap`s |
| Where the fields come from | The `GET` response alone. `options` carries the citation-style and PDF-processor enums, the tier ids and the timeout bounds, so the pane never restates the server's validation and a new enum member needs no UI edit |
| Inherit vs. set | Every input has an explicit inherit state — `INHERIT` (`''`) for the enums, an empty list for `languages` and `tiers`, `null` for the timeout. `overridesFromFormValues` **omits** those keys, because `normalizeOverrides` drops `undefined` and an absent key is the only way to say "fall back to the operator's config" |
| Why the fallback switch is a three-way select | `useThirdPartyBackup: false` and "unset" are different states: one pins the user to off, the other follows the operator. A `Switch` cannot express the difference |
| Seeded from `overrides`, not `effective` | Seeding the inputs from what is in force would turn every inherited field into an explicit override the moment the user saved anything, silently pinning them to today's server config. `effective` appears only as the `desc` text under each input and as the timeout's placeholder |
| After a write | The form re-renders from the response, not from what it sent — `PUT` validates and trims (a sixth language, an unknown tier, a 99s timeout clamped to 60) and the response is the authority |
| Server configuration group | The five `configured` booleans, read-only. They stay Worker secrets (2.3 of the to-do), so the pane shows status and never an input |
| i18n | The `qwksearch` namespace, not `setting` — the nav label reads `tQwkSearch('extraction.title')` the way Labs reads `tLabs('title')`. 48 keys in en-US and zh-CN |

Upstream edits are five registration points, no logic: the `SettingsTabs` enum
member, an entry in `componentMap.ts` and `componentMap.desktop.ts` (kept in
step by `componentMap.sync.test.ts`), the sidebar item in `useCategory.tsx`, and
the compact-header title map in `SettingsContent.tsx`.

**The drift guard is `contract.test.ts`.** `src/` bundles for the browser and
`worker/` for workerd, so `api.ts` restates the Worker's types instead of
importing them. That test is the one place the two halves meet: it imports the
real `extractSettings.ts`, rebuilds the exact document the route returns, and
runs a load → edit → save cycle back through `normalizeOverrides`. A citation
style, tier or override field added on the server and not in `api.ts` fails it.

### F5 — Search provider contract

The seam that makes LobeHub's agent search *QwkSearch's* index.

```
LobeHub web-browsing tool
  → SearchService (apps/server/src/services/search/index.ts)
    → SearchImplType.QwkSearch → QwkSearchImpl
      → GET {QWKSEARCH_SEARCH_URL}?q=…&cat=…&recency=…
        → Worker A: apps/qwksearch-web/app/api/agent/search
          → research-agent-ui createSearchHandler
            → search-web-api searchWeb() → search.qwksearch.com (SearXNG) → 100+ engines
```

| Concern | Behavior |
|---|---|
| Enable | `SEARCH_PROVIDERS=qwksearch` (set in `wrangler.jsonc` vars) |
| Endpoint | `QWKSEARCH_SEARCH_URL`, default `https://qwksearch.com/api/agent/search`; optional `QWKSEARCH_API_KEY` sent as a bearer token |
| Configuration | Every knob the request carries is resolved by `searchSettings.ts` — see F5a. `index.ts` only turns the resolved value into HTTP |
| Categories | Three vocabularies are normalized onto the endpoint's ten SearXNG names: LobeHub's manifest, QwkSearch's 13-category registry (`academic`, `social`, `tech`, `torrents`, …) and SearXNG's. A name none of them knows is dropped; a call left with nothing valid falls through to the configured default (`general` unless an operator set otherwise) rather than returning an empty page |
| Advertised categories | The manifest enum is resolved at module evaluation by `packages/builtin-tool-web-browsing/src/searchCategories.ts`. With `SEARCH_PROVIDERS=qwksearch` and nothing else, the model is offered all ten (`files`, `it`, `map`, `music`, `social+media` on top of LobeHub's five); any other configuration keeps LobeHub's five, so no backend is asked for a category it cannot serve |
| Fan-out | One request per category, issued in parallel, capped at `maxCategories` (3 by default, operator-raisable to 10) |
| Merge | Deduplicated by URL — highest score wins, engine lists union, a missing snippet is backfilled from the duplicate. Capped after the merge when `resultLimit` is set, so the cap counts distinct URLs and keeps the highest-scoring ones |
| Engines | Never forwarded. `useAutoSearchEngineSelection = true` tells `SearchService` not to retry by stripping engine restrictions, because QwkSearch already picks engines per category |
| Failure | Any category request failing raises `TRPCError SERVICE_UNAVAILABLE`, so `SearchService` can fail over to the next configured provider |

Four upstream lines are edited for this, all registration points: the
`SearchImplType` enum, the factory switch in
`apps/server/src/services/search/impls/index.ts`, and in
`packages/builtin-tool-web-browsing/` the manifest's import + enum expression
and one export line in `src/index.ts`. Everything else is new files —
`impls/qwksearch/` and `builtin-tool-web-browsing/src/searchCategories.ts`.

Note that `packages/**` is excluded from the root Vitest config and the
web-browsing tool package has no config of its own, so a test placed beside
`searchCategories.ts` would never run. Its coverage lives in
`impls/qwksearch/index.test.ts` instead, which imports the package by name.

### F5a — Search settings contract

The search-side mirror of F2a, and the first of the three steps the Search &
Sources pane needs. `QwkSearchImpl` used to read `process.env` inside a getter
and hard-code the rest: `general` as the fallback category, three categories per
query, and four query parameters the fan-out endpoint accepts that it never
sent. `searchSettings.ts` replaces all of it with one resolved `SearchSettings`,
folded out of three layers.

```
DEFAULT_SEARCH_SETTINGS              shipped behaviour
  ← searchSettingsFromEnv(env)       Worker vars + secrets   (operator)
  ← UserSearchOverrides              persisted preferences   (signed-in user)
  ← searchOverridesFromParams(p)     this tool call's args   (the model)
      ↓
  one GET per resolved category, carrying lang / recency / safesearch /
  publicInstances, merged and then capped at `resultLimit`
```

| Concern | Behavior |
|---|---|
| Validation | Every value is normalized on the way in — categories aliased onto the endpoint's ten names, language tags matched against a BCP-47 shape and case-canonicalized (`EN-us` → `en-US`), numbers rounded and clamped, enums matched case-insensitively. A value that fails falls back to the layer below; nothing throws, because a bad preference must not turn a search into a 500 |
| Layer asymmetry | `endpoint` and `apiKey` resolve **from the environment only** — a user-supplied backend URL would leak the configured bearer token to whatever host they chose. `RequestSearchOverrides` is narrower again: the tool call is written by the model, so it may narrow only `categories` and `timeRange`, the two fields the manifest offers it. `maxCategories` is withheld from it because it bounds how many upstream requests one query costs |
| Where the cap is applied | `maxCategories` truncates the category list once, after every layer has resolved — the list can arrive from the request layer while the bound comes from the user layer, so capping inside a layer would use the wrong bound |
| Empty is not a value | A normalizer that finds nothing valid returns `undefined`, not `[]`, so a typo in `QWKSEARCH_SEARCH_CATEGORIES` falls through to the layer above instead of searching nothing |
| `searchTimeRange: 'anytime'` | The manifest's "no filter" value is not one the endpoint understands, so it drops out of the request layer and whatever the operator configured stands — `undefined`, no filter, unless they set one |
| Diagnostics | `redactSearchSettings` replaces the credential with a boolean. `searchSettingsForClient` goes further for the future pane: it returns exactly the fields a user may change, reduces the endpoint and the key to presence flags under `configured` (an endpoint URL can carry basic-auth credentials in its userinfo), and serializes the two optional fields as `null` rather than omitting them, because absent means "inherit" everywhere else in this seam |
| Where the user layer lives | On D1, as of F5b — the search-side mirror of F2b |

Env vars, all optional and all defaulted: `QWKSEARCH_SEARCH_CATEGORIES`,
`QWKSEARCH_SEARCH_MAX_CATEGORIES`, `QWKSEARCH_SEARCH_LANGUAGE`,
`QWKSEARCH_SEARCH_TIME_RANGE`, `QWKSEARCH_SEARCH_SAFE`,
`QWKSEARCH_SEARCH_PUBLIC_INSTANCES`, `QWKSEARCH_SEARCH_RESULT_LIMIT`. The
existing `QWKSEARCH_SEARCH_URL` and `QWKSEARCH_API_KEY` keep their names, so no
deployment needs to change; setting none of the new ones reproduces the
behavior the impl had before the settings layer existed, with one deliberate
addition — `lang=en-US` is now sent explicitly, which is the value the endpoint
already defaulted to.

The module lives beside its consumer in `impls/qwksearch/` rather than under
`worker/` (where `extractSettings.ts` sits) because the dependency runs
worker → `@/server/*` and never back: the `/api/doc/search-settings` route in the
Worker imports this, and this could not have imported from `worker/`.

### F5b — Search preferences contract

F5a defined a user layer and gave it no storage. This is that storage, its API,
and the path that carries it into a live search.

```
GET/PUT/DELETE /api/doc/search-settings   (worker/routes/qwksearch/searchSettings.ts)
  → searchPreferences.ts
    → D1 `search_settings` (userId PRIMARY KEY, overrides JSON, updatedAt)

web_search tool call
  → webBrowsingRuntime.factory({ userId, … })      ToolExecutionContext
    → new SearchService({ userId })
      → createSearchServiceImpl(type, { userId })
        → new QwkSearchImpl({ userId })
          → userSearchOverridesFor(userId)         ← the same table, once per impl
            → resolveSearchSettings(env, userOverrides, callOverrides)
```

| Concern | Behavior |
|---|---|
| Storage | One row per LobeHub Better Auth user id, on the same D1 database as `extraction_settings`. A JSON blob, not a column per setting, for F2b's reason: the type is the schema |
| Where it lives | `apps/server/src/services/search/impls/qwksearch/searchPreferences.ts`, under `@/server/*` — **the one place the two settings features are not twins.** Extraction's preferences sit in `worker/` because only Worker routes read them; these are read by `QwkSearchImpl` too, which is `@/server/*` code, and the dependency runs worker → `@/server/*` and never back. Only this placement serves both consumers |
| Where the table is declared | Here, and re-exported by `worker/qwksearch/schema.ts` so that file stays the one list of QwkSearch D1 tables and the table keeps exactly one definition |
| How it reaches D1 | `getCfEnv` from `@/database/core/cloudflare`, the bridge the database package already uses to reach the Worker bindings — not `worker/qwksearch/db.ts`, which would be the backwards import. Cost: a second thin drizzle wrapper over the same `DB` binding |
| How the user id reaches the impl | Threaded through the four constructors above. F5a flagged this as the open question, since the impl is built by a factory with no request in scope; the answer is that the factory's `ToolExecutionContext` already carries `userId`. The rejected alternative, a per-request impl factory on `SearchService`, would rebuild all twelve providers per query to serve one |
| Read frequency | Once per impl, not per query — `overridesFor()` memoizes the promise, so a turn that fans out several searches pays one D1 read and concurrent queries collapse onto it. An impl is built per tool execution, so there is no staleness window |
| Validation | Twice — `normalizeSearchOverrides` on write and again on read, per F2b. The read pass is what keeps a row from an older build out of a live request |
| Response shape | `{ overrides, effective, options }`, the same three parts F2b returns. `options` carries the ten categories, the four recency filters and the numeric bounds, so a new category never needs a matching UI edit |
| What cannot be stored | `endpoint` and `apiKey`. `UserSearchOverrides` excludes them at the type level and the route proves it at runtime: `PUT`ing either stores neither, and `GET` reduces both to presence flags under `effective.configured` |
| Write semantics | PUT replaces rather than merges and echoes what was stored; DELETE returns the user to the operator's configuration — F2b's semantics exactly |
| Auth | All three verbs require a session. The anonymous equivalent is the `searchCategories` / `searchTimeRange` arguments the tool call already carries |
| Anonymous cost | A search with no `userId` skips the read entirely rather than querying for a row that cannot exist |
| Failure | Reads never throw: an unreadable row, unparseable JSON, a D1 outage, or no D1 binding at all resolves to `{}` and the search runs on the operator's configuration. The impl catches as well as the storage module, so an injected loader cannot break that guarantee and a rejection is never what the memo caches. Writes are the opposite and propagate, so the pane can say a preference was not saved |

Precedence, lowest to highest: shipped default → Worker env → the user's saved
overrides → the tool call's own arguments.

Four upstream LobeHub files are edited, each by one line of signature or call:
`services/search/index.ts` (the `SearchService` constructor takes options),
`services/search/impls/index.ts` (`createSearchServiceImpl` forwards them),
`services/toolExecution/serverRuntimes/webBrowsing.ts` (passes `userId`), and
`services/search/index.test.ts` (five assertions on the factory's arity).
`worker/app.ts` gains one mount line. The route, the preferences module and the
migration are new.

## 3. Shared infrastructure

Both Workers point at the **same** Cloudflare resources, which is what makes a
gradual cutover possible at all.

| Binding | Resource | Shared with `apps/qwksearch-web`? |
|---|---|---|
| `DB` | D1 `qwksearch-new` (`b0ba9a66-…`) | ✅ same database id |
| `KV` | KV `c53d894414bb…` | ✅ same namespace id |
| `R2` | `qwksearch-uploads` | ✅ |
| `EMAIL` | Email Routing → `noreply@qwksearch.com` | ✅ |
| `HYPERDRIVE` | Postgres for LobeHub's 169-table schema | ❌ engine-only |
| `ASSETS` | SPA bundles | ❌ engine-only |

D1 tables the engine reads and writes: `articleCache`, `articleQA`, `favorites`,
`documents`, `research_quotes`, `share_tokens`, `google_docs_sync` — created
idempotently by `migrations/d1/0001_qwksearch_tables.sql` — plus
`extraction_settings` (F2b) from `0002_extraction_settings.sql`. `bun run
cf:d1:migrate` runs both, and both are safe to re-run.

LobeHub's own data stays on Postgres (169 tables, 211 `jsonb` columns, 11
`pgvector` columns, ~380 raw SQL fragments, 157 migrations). Porting it to D1
would be a rewrite of the data layer, not a runtime port.
